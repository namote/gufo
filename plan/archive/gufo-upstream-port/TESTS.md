- "각각 단계에 테스트를 최대로 하면 오래걸리니까 테스트는 짧게 할수 있게 설계하자."

- "필요할때 만 하면되니까 최종점검은 할수있게 해줘", "두시간이든 세시간이든 최종점검에서는 해야될것 같아"

## 기본 규칙 (2026-10-28)

사용자: "수정살짝하고. 간이테스트 돌리고 10분? 효과있으면 또 더하고.. 만족스로운 성과가 나오면 전체테스트", "맨날 실패하면서 왜 맨날 돌리는거지?"

- **기본은 간이 검사다.** `make_plan.py`의 기본 `--tier quick`(선택된 GPU unit, T2, 창이 선택되면 T3)으로 20분 안에 끝낸다. 결과는 좋아짐/같음/나빠짐/노이즈로만 읽고, 5 %·3 ms 판정과 ABBA는 하지 않는다.
- 효과가 있으면 다음 수정으로 넘어가 다시 간이 검사를 돈다. 단계를 마칠 때만 `--tier stage`(T4s 축소판과 선택된 suite, pr tier, 1시간 안)를 돈다.
- **최종점검 F는 사용자 확인 뒤에만 돈다**(운영 전환 제안·PR 직전). `--tier final --final-approved "<사용자 말>"` 없이는 F plan이 만들어지지 않는다. `PLAN-P1.json`·`PLAN-F*.json`을 직접 복사해 탐색 단계에 쓰지 않는다.
- **디스크를 먼저 확보한다**(2026-10-28, 사용자: "디스크 용량을 확보후 진행하는거도 좀 추가해줘 금방차네"). 루트 SSD가 창별 `receipt/cache-disk`로 99 %까지 찼고, 찬 디스크에서 잰 복원 시간은 쓸 수 없었다. GPU 창 전에 `df -h /`로 여유를 보고 150 GiB 아래면 지난 `tmp/test-results`의 cache-disk부터 정리한다(결과 파일은 남긴다). `window.py`는 150 GiB 아래에서 창을 거부하고, 창이 끝나면 cache-disk 크기를 기록한 뒤 지운다. 모델 다운로드·nix 빌드처럼 크게 쓰는 작업도 시작 전에 여유를 본다. 크게 지운 뒤에는 `sudo -n fstrim -v /`를 돌리고 로그를 남긴다. 디스크 복원(cache-disk) 시간을 재는 창 동안에는 다른 세션의 다운로드·큰 쓰기를 멈춘다. 같은 바이너리에서 복원이 100 ms와 450~1100 ms로 갈리던 것이 정리·trim·쓰기 중단 뒤 66~207 ms로 모였다(`um3-trim-a01`, 2026-10-28).
- **늘 실패하는 원본 테스트는 돌리지 않는다.** `test/experiments/gufo_upstream_port_20261023/known_failures.json`의 `skip` 항목(Q4_K_M의 `conversation`, `--think off`의 `reasoning-budget`)은 quick·stage에서 빠진다. F에서는 돌리되 시그니처가 같으면 known_failure로 분류하고, 다른 실패만 새 실패로 본다. 원본 테스트 파일은 지우지 않는다(병합 충돌·PR 오염). 테스트 설계가 틀린 경우는 고쳐서 원본에 PR로 낸다.

## 목표 시간

|언제|도는 것|목표(빌드 포함)|
|---|---|---|
|수정 하나마다|바뀐 부분의 T0·T1 + T2 경우 일부|**20분 안**|
|단계 끝|T0~T3 전부 + T4s(축소 장문)|**1시간 안**|
|**최종점검 F**(필요할 때만)|실제 길이 전부. 아래 "최종점검" 절|**2~3시간 허용**|

- 평소(수정·단계 끝)에는 표의 시간을 넘기지 않는다. 넘기면 검사를 늘리지 않고 경우를 줄이거나 나눈다.
- 실제 길이 검사는 최종점검에서만 하고, 거기서는 시간이 걸려도 줄이지 않는다.

## 원칙

- **긴 문맥은 16K 축소판으로 대신한다.**
  - paged 동작(블록 할당·공유·CoW·회수·대기)은 문맥 길이의 절대값이 아니라 블록 수와 풀 비율에 달려 있다.
  - 16K는 64행 블록으로 256개, 256행 chunk로 64개다. 여러 블록 공유·CoW·축출을 보기에 충분하다.
  - 그래서 세션 수와 "풀 ÷ 세션 최대 문맥 합"의 비율을 운영과 같게 두고, 문맥만 16K로 줄인다(아래 축소표).
- **절대 길이에서만 생기는 문제는 따로 막는다.**
  - 큰 위치의 주소 계산: T1 커널 검사가 합성 KV로 위치 200K 이상을 직접 채워 본다.
  - 256K 기준 블록 수 계산: T0이 256K 숫자로 예약·한도를 계산해 본다.
  - 실제 256K 실행은 최종점검(F)에서 한다.
- **입장 검사는 짧은 prompt와 큰 `max_tokens`로 한다.** 예약이 `prompt + max_tokens`라서, 짧은 prompt로도 문맥 전체 예약을 만들 수 있다. 긴 생성이 시작되기 전에 취소한다.
- **기준 출력은 한 번만 만든다.** U0에서 원본 빌드의 greedy 출력 토큰 ID를 경우마다 기록하고, 이후에는 그 기록과 비교한다. 원본 최신으로 다시 맞출 때만 새로 기록한다.
- **바뀐 부분만 돈다.** 수정마다 바뀐 파일로 고른다.
  - 커널 → T1의 해당 커널
  - 풀·예약 → T0의 해당 테스트 + T2 입장·대기
  - 어댑터·복원 → T2 복원 경우
  - 빌드도 원본 `AGENTS.md`대로 해당 타깃만 한다.
- **서버는 설정마다 한 번만 띄운다.** 재시작 검사만 한 번 더 띄운다. DeepSeek(가중치 81 GiB)처럼 로드가 긴 모델에서 특히 중요하다.
- **실패는 그대로 남긴다.** 다른 경로나 설정으로 자동 재시도하지 않는다(프로젝트 규칙).

## 축소표 (운영 → 검사)

|운영·이전 측정|검사(T4s)|맞추는 것|
|---|---|---|
|256K × 4세션, 풀 40 GiB(꽉 찬 256K 2.5개분)|16K × 4세션, 풀 = 16K 2.5개분|세션 수와 풀 비율|
|64K × 8세션, 풀 24 GiB(꽉 찬 64K 6개분)|16K × 8세션, 풀 = 16K 6개분|세션 수와 풀 비율|
|256K 장문 1건·재시작 복원|16K 장문(중간에 정답 문자열) cold → 다음 턴 → 재시작 복원|단계 흐름. 실제 256K는 운영 전환 제안 직전 1회만|
|32K 장문 2대화|8K 장문 2대화|대화 사이 공유·축출|
|대화 여러 개 회귀(regress·boundary·shared)|같은 시나리오를 턴당 1~2K로|경계 수와 순서|

축소판은 정답 여부, 출력 토큰 ID, 블록·복원 수치를 본다. 시간 비교는 같은 축소 조건의 기준값과만 한다.

### T0 CPU

- 원본 가짜 어댑터(`tests/cache/fake_adapter.hpp`) 위에 공통 풀·블록 테이블을 검사한다.
  - 할당·해제·참조 수
  - CoW(공유 블록에 쓰면 복사본을 만든다)
  - 예약(`prompt + max_tokens` 블록 수, 재사용 prefix 블록은 빼고 셈). 16K와 256K 숫자 둘 다
  - 풀이 모자랄 때 대기열로 가는지
  - 오름차순이 아닌 블록 id에서 주소 계산
- 어댑터 주소 계산(`BorrowRowsView`·`TransferRows`의 블록 테이블 경로)을 CPU 메모리로 검사한다.

### T1 커널 동등성

- KV 쓰기와 attention(prefill·decode·batched decode·검증)을 paged 테이블과 연속 배치로 각각 돌려 출력을 bit 단위로 비교한다.
- 합성 KV로 위치 0, 블록 경계 앞뒤, 200K 이상을 직접 채운다. 블록 id는 섞어서 준다.
- 모델마다 해당 component만 본다.
  - Qwen 27B: attention K/V
  - Flash-Next: key·value·pooled keys
  - Gemma 4: global K/V(층마다 head 수가 다름)
  - DeepSeek: 압축 KV 풀(구조 확인 뒤)

### T2 짧은 서빙 경우

설정: 문맥 16K, 세션 2~4, greedy, 생성 32토큰 이하, prompt 8K 이하.

|경우|확인|
|---|---|
|cold 짧은 대화 2개|출력 토큰 ID가 기준과 같다|
|같은 대화 다음 턴|살아 있는 상태를 재사용한다(재사용 토큰 수 = 기대값)|
|다른 슬롯으로 복원(checkpoint)|출력 동일, 복원 토큰 수와 복사량 기록|
|공통 앞부분 요청 2개 동시|리더·팔로워 동작, 출력 동일|
|입장 예약|짧은 prompt + `max_tokens` 남은 문맥 전부로 세션 수만큼 동시에 보낸다. 풀 계산대로만 들어가고 나머지는 대기하는지, 끝난 뒤 블록이 모두 돌아오는지 본다|
|재시작 디스크 복원 1회|다음 턴이 디스크에서 복원되고 출력이 같다|
|이미지 1장(이미지 모델만)|정답, 출력 동일|
|DFlash2/MTP/DSpark를 켠 경우|greedy 출력이 AR 기준과 같다(원본 품질 계약)|

### T3 짧은 bench

- `gufo bench` 측정점: pp2048·tg128을 깊이 0과 8K에서 각각 3회 돈다.
- 커널이나 핫 경로를 바꾼 수정에서만 돈다.
- 같은 날 기준 빌드 값과 비교한다. 5 %를 넘으면 그 측정점만 번갈아 다시 잰다(원본 규칙과 같음). 그래도 넘으면 실패로 남긴다.

## 최종점검 F (필요할 때만, 2~3시간 허용)

**언제:** 아래 경우에만, 사용자 확인 뒤 돈다.
- 운영 전환을 제안하기 직전
- 원본·포크에 PR을 내기 직전
- 사용자가 요청할 때
- 축소판에서 설명되지 않는 이상이 보일 때

**무엇을** (실제 운영 길이·설정, 축소 없음):

|항목|내용|
|---|---|
|장문|32K·256K 실제 prompt cold → 다음 턴 → 재시작 디스크 복원, 정답|
|세션 밀도|256K × 4·풀 40 GiB, 64K × 8·풀 24 GiB 실제 기동과 동시 요청 정답|
|대화 회귀|이전 비교 시나리오 전부(대화 2개, regress, boundary, shared, 32K, 256K) 실제 길이|
|메모리·디스크|host 최대 메모리, SSD 쓰기량, 디스크 사용량. 운영 Manager 예산(로드 64 + 작업 14 GiB) 안인지|
|시간|요청별 TTFT를 기준 빌드와 비교(5 %·3 ms, 원본 규칙)|
|bench|`gufo bench` 전체 행렬(PLAN-R4와 같은 측정점)|
|원본 suite|원본 `tests/functional`의 `long-context`·`cache` suite 전체(PR 직전에는 main과 번갈아)|
|모델 확장분|확장한 모델마다 같은 항목을 그 모델 운영 길이로|

**어떻게:**
- 실행기 하나(`test/experiments/gufo_upstream_port_20261023/final.py`, 계획 `PLAN-F*.json`, 원본 suite 드라이버 `suite.py`)로 위 항목을 순서대로 돈다. `--only`로 창을 골라 돌 수도 있다. 첫 결과는 [F 결과](F-RESULTS.md)
- 중간에 실패해도 다음 항목은 계속 돌고, 실패 항목과 원인을 그대로 남긴다(자동 재시도 없음).
- 이전 최종점검과 같은 빌드·설정이면 다시 돌지 않고 그 결과를 쓴다.
- 결과는 `storage/evaluations/gufo-upstream-port-final-*/`에 보존한다.

## 원본 PR 직전

- 원본 규칙은 연속 대화 변경에 `long-context`·`cache` suite를 요구하고, main과 PR을 번갈아 돌리라고 한다.
- PR 직전에는 최종점검 F를 돈다. 원본 suite 전체를 main과 번갈아 도는 것도 F에 들어 있다.
- 단계마다 원본 suite를 돌리지는 않는다.
