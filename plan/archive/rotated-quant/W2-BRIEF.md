# W2 브리프: R0 품질 하네스와 기준선 (2026-10-29)

이 브리프는 [W-COMMON.md](W-COMMON.md)와 [R-BRIEF.md](R-BRIEF.md)를 따른다. 범위는 PLAN 단계 표의 "R0 기준선"과 "효율 점수판", 그리고 D4의 한국어 세트 초안이다.

## 목표

여러 양자화 파일을 BF16과 같은 기준으로 비교하는 품질 하네스를 만들고, 기존 파일들로 기준선을 잰다. 이 하네스는 R2 ②, R3, R4에서 모두 그대로 쓴다. 그러니 다시 쓰기 쉽게 만든다: 모델 파일 하나를 넣으면 같은 형식의 결과가 나와야 한다.

## 1. 평가 코퍼스 (약 32K 토큰)

- 구성: 영문 산문, 한글 산문, 코드, 대화(채팅 템플릿을 적용한 것)를 대략 같은 비율로 담는다.
- 출처는 라이선스가 분명한 것만 쓴다(예: 퍼블릭 도메인, CC-BY, 저장소 안의 MIT 코드). 출처와 라이선스를 기록한다.
- 27B 학습 데이터에 그대로 들어 있을 가능성이 큰 유명한 글(위키백과 대표 문서 등)은 피한다. 피할 수 없으면 그 점을 적는다.
- 저장 위치: 코퍼스를 만드는 스크립트와 manifest(출처, 라이선스, 구간별 토큰 수, sha256)는 저장소에 둔다. 원문이 크거나 저장소에 넣기 곤란하면 `~/projects/ai.tools/storage/` 아래에 두고 해시로 고정한다. 어느 쪽으로 했는지 결과에 적는다.
- R3 imatrix 보정 코퍼스와 겹치면 안 된다. 그래서 출처 목록을 W4가 피할 수 있게 manifest에 남긴다.
- 문맥 길이: 4K 안팎의 창 여러 개로 나눠 teacher forcing한다. 창 크기와 겹침을 기록한다.

## 2. logits 수집과 지표

- BF16 기준 실행에서는 위치마다 top-k(예: k = 64, 근거를 적는다)의 토큰 id, logit, 전체 logsumexp를 저장한다. 비교 대상 실행에서도 같은 위치의 같은 정보를 저장한다.
- 지표는 BF16 대비로 낸다.
  - paired NLL 차이
  - top-k 절단 KL. 절단 방식(나머지 질량을 어떻게 처리하는지)을 명시한다.
  - top-1 일치율
  - 각각에 토큰 단위 paired bootstrap 95% 신뢰구간. 창 단위 블록 bootstrap도 함께 내서 둘을 비교한다.
- **수집 경로:** gufo에는 teacher forcing으로 위치별 logits를 내보내는 기존 도구가 없을 수 있다(`gufo eval`은 HTTP 문항 평가다). 먼저 찾는다: `tools/qwen27b/check.py`, `tests/models/qwen27b/`의 logits 비교 테스트, 엔진 API.
  - 없으면 모델 옆 도구(`tools/qwen27b/` 또는 `tests/models/qwen27b/` 아래의 C++ 실행 파일이나 Python)로 만든다. decode 경로와 prefill 경로를 고를 수 있게 한다(R2 ②가 경로마다 확인해야 한다).
  - `src/`를 바꿔야 하면(예: 모든 위치의 logits를 돌려주는 엔진 훅) **멈추고 감독에게 보고한다.** `src/`는 W3이 바꾸므로 감독이 순서를 정한다.
- DFlash2 verify 경로의 logits 비교는 R2 ②에 필요하다. 이번에는 수집 경로를 설계만 해 두고, 구현이 크면 범위를 보고한다.

## 3. 측정 대상과 속도

- 품질: BF16(기준), Q8_0, Q6_K(bartowski), UD-Q4_K_XL, Q4_K_M, GSQ-RCO-IQ3_S. 경로는 `~/projects/ai.tools/storage/models/llm/` 아래 `qwen-3.8-27b-*`와 `qwen3_8-27b-gsq-rco-iq3_s-*`다. 파일마다 sha256을 기록한다. 이미 기록된 해시가 있으면 그것을 쓴다.
- 속도: 같은 날 같은 바이너리로 다음을 잰다.
  - pp2048/tg128을 d0과 d32K에서
  - DFlash2 수락률과 실효 tok/s(드래프터는 `qwen-3.8-27b-dflash2-gguf/`)
- 측정 바이너리는 운영과 같은 툴체인(ROCm 10.1, W-COMMON의 rocm101 이미지)으로 HEAD에서 빌드한다. 리비전과 툴체인을 기록한다.
- 속도 판정은 요청·단계별로 5 %·10 ms 기준이다. 같은 파일을 번갈아 돌려 잡음 폭을 기록한다. 잡음이 크면 결론 없음으로 둔다.
- 신뢰구간 폭이 Q4_K_XL과 Q4_K_M의 차이보다 충분히 좁지 않으면, 코퍼스를 늘리자고 제안한다.
- 상주 메모리(HIP가 보고하는 최대값)도 기록한다.

## 4. D4 한국어 프롬프트 세트 초안

지시 따르기, 요약, 코드 설명, tool-call을 각각 몇 개씩 넣는다. 평가 코퍼스와 보정 코퍼스 둘 다와 겹치지 않게 한다. 판정 방식은 제안만 한다. 수치 기준은 사용자가 정한다.

## 순서와 허락

1. 기존 도구를 조사하고, 코퍼스를 만들고, 하네스 코드를 쓴다. CPU 테스트(합성 logits로 지표와 bootstrap 검증)까지 한다.
2. **WAITING:** 빌드가 필요하면 무거운 CPU 작업 허락을 받는다.
3. **WAITING:** GPU 창 계획(모델 순서, 예상 시간, 디스크)을 보고하고 허락을 받는다. 창은 품질 창과 속도 창으로 나눠도 된다. BF16 기준 실행이 먼저다.
4. 결과와 원시 파일을 정리하고, `R0-RESULTS.md`와 `RESULTS.md` 첫 표를 쓴 뒤 커밋하고 보고한다.

## 통과 기준

- 모델별 품질·속도 표에 신뢰구간과 잡음 폭이 있다.
- 코퍼스 해시가 기록되어 있다.
- 하네스는 회전 파일이 들어와도(W3 로더 이후) 코드를 바꾸지 않고 돌릴 수 있다.
