# Flash-Next 동시 접속 성능 계획 (2026-11-11)

## 목표

1. **단일 요청:** 지금 속도를 유지한다. 새 경로는 요청이 2개 이상일 때만 켠다.
2. **동시 디코드:** 여러 세션의 디코드를 한 패스로 묶어(batched decode), 합계 tok/s가 단일보다 높아야 한다.
3. **동시 프리필:** N개가 동시에 프리필할 때 각 요청이 최소 `단일 최대 속도 / N`을 낸다.
4. **프리필 + 디코드:** 디코드가 굶지 않는다(9910a9f4에서 해결). 프리필은 가능한 한 단일 속도에 가깝게 낸다. 후보 방법은 혼합 배치.

## 현재 상태

- **e015a85d (운영 설정):** c03, 1M YaRN(배율 4), KVarN K4V4, 세션 2개.
- **9910a9f4 (시간 분배 스케줄러):** 디코드가 활성인 동안 프리필 조각 하나가 쓴 시간(10ms 이상, 최대 1s)만큼 디코더가 연속으로 돌고, 그다음 조각이 돈다. 운영 runtime은 `runtime-20261111b`.
  - 이전(번갈아 처리): 425K 프리필 중 디코드가 3.5 tok/s였다.
- **배치 디코드:** `Executor::ForwardBatch`가 이미 있다. 최대 8세션, 세션당 8행. 디코더가 하나뿐이면 `serial-fallback`이다.
- **혼합 배치 조사 결과:** 프리필과 디코드가 한 패스에 들어가는 경로는 없다. 확장할 지점과 걸림돌:
  - 확장 지점은 `ForwardBatchImpl`(executor_batch.cpp:904)에 "prefill" BatchItem 종류를 추가하는 것이다.
  - 걸림돌:
    - 전역 `prefill_phase` 산술 모드(executor_internal.hpp:146)
    - GDN 청크 스캔이 세션 하나만 처리함
    - KVarN staging이 executor 전체에서 하나뿐임 → 패스당 프리필 1개만 가능
    - EXL3 MoE prefill 경로
    - 프리필 행의 MTP kv_only 패스
    - 로짓은 디코드 행만 계산해야 함

## 결과 요약 (2026-11-11 저녁)

- **S0:** 측정 완료. 목표 1~3은 추가 변경 없이 충족한다.
  - 단일 속도는 그대로 유지된다.
  - 디코드 2개를 배치로 돌리면 합계가 단일의 1.48배다.
  - 프리필 2개를 동시에 돌리면 각각 단일 속도의 절반을 넘는다.
- **S1, S2:** 할 일 없음. 목표를 이미 충족한다.
- **S3 혼합 배치:** 하지 않기로 했다.
  - 조각 시간은 약 0.2 s + 0.8 ms/token이고, 고정분은 trunk 패스 안에 있다. 프리필 크기 패스가 전체 가중치를 한 번 읽는 비용으로 추정한다.
  - 혼합 패스도 이 고정분을 똑같이 진다. 그래서 디코드는 패스당 약 3.5토큰, 최대 약 15 tok/s다. 시간 분배는 20 tok/s를 낸다.
  - 근거와 수치: docs/GFX1151-KNOWHOW.md "S0 concurrency matrix".
- **④ 조각 크기:** 512를 유지한다. 1024는 130 s 프리필에서 약 1 s를 줄이지만 디코드 끊김이 두 배가 된다.

## 단계 (순서대로, 각 단계마다 구현 → 검토 → 운영 적용)

### S0. 기준 측정 (구현 없음)

`host_preflight.sh`를 돌린 뒤 같은 조건에서 아래 네 상황을 한 번에 잰다.

| 상황 | 측정 내용 |
|---|---|
| ① 단일 | pp(짧은 입력/32K/128K), tg |
| ② 디코드 2개 동시 | 각 tg, 합계 tg, execution_plan(batched-w2인지) |
| ③ 프리필 2개 동시 (각 32K, 128K) | 각 pp, 합계 pp를 단일 pp와 비교 |
| ④ 프리필(128K 이상) + 디코드 | 디코드 wall tok/s, 프리필 pp |

- 하네스: `tools/bench/` 또는 `plan/serving/concurrency_bench.py`(새로 작성).
- 결과는 KNOWHOW에 기록한다.

### S1. 동시 디코드 배치 확인/수정 (목표 2)

- ②에서 `batched-w2`가 아니거나 합계가 단일보다 낮으면 원인을 찾아 고친다.
  - 확인할 곳: `SelectDecodePlan`, MTP 배치 컨트롤러, 스케줄러가 디코더를 모으는 방식.

### S2. 동시 프리필 공정성/손실 (목표 3)

- ③에서 각 요청이 `단일 / 2`보다 낮으면 조각을 바꿀 때 생기는 비용을 줄인다.
  - 후보: 조각 크기, PLE prefetch, KVarN staging/plan, 세션 전환 비용, 2048 admission 조각.

### S3. 혼합 배치 (목표 4)

- **방법:** `ForwardBatchImpl`에 프리필 항목 하나(패스당 1개)를 추가한다.
  - 공유: projection, MoE, HC 패스는 모든 행을 함께 처리한다.
  - 항목별: GDN과 attention은 항목마다 따로 처리한다. 프리필 항목은 prefill 산술(WMMA 등), 디코드 항목은 decode 산술을 쓰도록 행 범위로 경로를 나눈다.
  - 로짓은 디코드 행에 대해서만 계산하고, 프리필은 마지막 조각일 때만 계산한다.
  - MTP kv_only는 프리필 항목에 대해 패스 뒤에 따로 돈다.
- **조각 크기:** 혼합 패스 시간이 목표 디코드 지연(예: 150ms)이 되게 적응적으로 잡는다.
  - 패스 시간이 대부분 프리필 조각이므로 512 고정이면 디코드가 약 6 tok/s로 떨어진다.
- **기대 효과:** 디코드는 S0 ④ 수준을 유지하고, 프리필은 50%에서 약 80% 속도로 올라간다. 정확한 값은 S0 ④에서 디코드 패스가 차지하는 비중으로 다시 계산한다.
- **품질:** 디코드 행의 산술 경로가 바뀌어 bit-exact가 아닐 수 있다. 허용하되 다음으로 판정한다.
  - MTP acceptance
  - KL/top1(serial 대비)
  - 기능 테스트(long-context, cache)
- **러너 API:** 스케줄러는 러너가 지원하고 프리필과 디코드가 모두 있을 때만 혼합 단계를 쓴다. 그 외에는 현재 시간 분배로 떨어진다.

### 마무리

- 각 단계를 운영에 적용할 때 할 일:
  - runtime 디렉터리를 새로 만든다.
  - `gufo-server.py`의 RUNTIME/SHA를 갱신한다.
  - install, 재시작한다.
  - ①~④ 중 영향받는 항목만 다시 잰다.
- 되돌리기: 이전 runtime 디렉터리로 RUNTIME/SHA를 되돌린다.
