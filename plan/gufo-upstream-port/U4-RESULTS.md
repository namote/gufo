# gufo 원본 이식 U4 결과: checkpoint KV 행을 장치 블록 참조로 (2026-10-24)

상위 문서: [이식 계획](PLAN.md), [U4 설계](U4-DESIGN.md), [U5b 결과](U5B-RESULTS.md).

## 구현

gufo `ai-tools/port-u4`(`3942939b`에서 분기)의 커밋은 다음과 같다.

- `833246db`: checkpoint가 공유 풀의 KV 블록을 참조로 갖는다(행 사본 없음). 공유 블록에 쓰기 전에 CoW하고, 다른 슬롯으로 복원할 때는 블록을 매핑한다. 풀이 모자라면 checkpoint만 쥔 블록부터 비운다(`checkpoint_dropped reason=row_capacity`). 입장 여유는 1 → 2블록(CoW 몫)이다.
- `3c600e8a`: GPU 테스트 수정. 한 번만 쓸 수 있는 전송 stream을 여러 번 써서 테스트가 실패했다. 제품 경로에는 해당하지 않는다.
- `17ef4326`: 이어지는 대화(cache hit, prefill_offset ≠ 0)에서는 stable 경계가 frontier 64토큰 안이면 거기서 멈추지 않는다. 처음 오는 prompt는 그대로 멈춘다.
  - U4로 checkpoint 비용이 작아지자 이 capture가 더는 거절되지 않았다. 그래서 256K 다음 턴의 33토큰 prefill이 255K 문맥 pass 2번이 됐다(a01: 0.94 → 1.81 s).

CPU 테스트는 127/127 통과다. 새 cache 테스트 4개는 수정 없이 실패하는 것을 확인했다.

## GPU 창

- 창은 F2와 같다(256K × 4, 풀 40 GiB, RAM 8 GiB, 디스크 64 GiB). 운영 `210c7633`과 번갈아 돌렸다.
- 실행기는 `final.py --set f4`(`PLAN-F4.json`)이다.
  - `final-f4-a01`: `833246db`. GPU 테스트 실패와 256K 다음 턴 회귀를 발견했다.
  - `final-f4-b01`: `17ef4326`.
- `final-f5-a01`은 U4에 RAM 예산 2 GiB이다(`--set f5`, 이식본만).

**정확성**
- GPU 단위 테스트: 전부 PASS. 새 `retained_kv_blocks`도 통과했다. 이 테스트는 매핑 복원, 참조 수, 디코드 동일, 재기록 CoW, reset 뒤 블록 반환을 검사한다.
- 텍스트: 모든 창에서 운영·8 GiB 이식본(U5b)과 같다.
- T2: 21/21 같다(b01, f5 모두).

- **256K 재시작(디스크)은 U4 회귀로 보지 않는다.**
  - 같은 U5b 코드에서도 디스크 읽기 시간(`filesystem_ms`)이 run마다 1.78 / 4.97 / 4.97 / 7.05 s였다(a06 / a03 / a04 / a05).
  - U4 값은 4.20 / 5.22 / 4.33 s(a01 / b01 / f5)로 그 범위 안이다. 창 순서도 모든 run에서 같다.
  - 운영의 디스크 복원은 대개 3.2–3.8 s이다. 이식본 디스크 읽기가 느리고 흔들리는 것은 U4와 별개의 남은 항목이다.
- shared c1(첫 팔로워)은 그대로다. U4b로 고친다.

**메모리**

컨테이너 cgroup `memory.stat` 최대 anon(GiB)이다.

|창|운영|U4 8 GiB|U4 2 GiB|
|---|---|---|---|

- **anon은 같은 예산의 U5b와 거의 같다.** U5b는 8 GiB에서 23.1–24.9 GiB, 2 GiB에서 19.5–19.6 GiB였다.
- 이유: RAM 예산은 상한이고, 이식본은 그 상한까지 checkpoint를 남긴다.
  - U4에서는 행 사본 대신 private 상태(개당 약 245 MB), tail, 메타데이터를 가진 checkpoint가 더 많이 남는다.
  - shared 창의 장부는 약 6.5 GB를 쓴다. 시작 때 committed backing은 2.27 GB(2 GiB 예산이면 1.90 GB)이다.
- 같은 메모리에서 비교하면 U4는 TTFT를 덜 잃는다. 2 GiB에서 U5b와 비교한 값이다.
  - shared 합 63.1 → 60.4 s, two8k 재시작 뒤 1.85 → 1.51 s.
  - 32K 재시작 뒤 T3는 0.85 → 3.91 s로 나빠졌다. 2 GiB에서 어떤 checkpoint가 남느냐에 따라 달라진다.
- 예산을 1 GiB까지 낮춰도 이식본 anon은 운영보다 약 1.5–2 GiB 많다(f3 18.7 GiB). 예산과 관계없는 바닥이다.
  - 정정(2026-10-24, [anon 바닥](ANON-FLOOR-RESULTS.md)): 예산과 관계없는 부분은 DFlash2 prompt feature pinned 버퍼 1.56 GiB(원본 #688)와 나머지 약 0.5 GiB다. 이와 별도로 예산 중 최대 2 GiB를 시작 때 미리 커밋한다.

## 판정

- **채택:** 정확성이 같고, RAM 복원 TTFT가 U5b보다 좋다. 같은 RAM 예산에서 더 많은 checkpoint를 담는다.
- **메모리 목표(운영 ±1–2 GiB)는 U4만으로는 이루지 못했다.** 8 GiB 예산에서는 예산을 채운다.
  - 운영 수준 메모리는 예산을 낮추는 결정(1–2 GiB)이 필요하다.
  - 그때 잃는 shared 첫 팔로워(14 s)는 U4b(tail checkpoint, 약 3 × 245 MB)로 되찾는 것을 U4b 창에서 확인한다.
- **남은 항목:**
  - 이식본 디스크 복원 읽기의 편차(256K 1.8–7 s).
  - 예산과 관계없는 anon 바닥 +1.5 GiB.
