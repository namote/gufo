# gufo 원본 이식: 디스크 복원 읽기 편차의 원인 (2026-10-24)

상위 문서: [이식 계획](PLAN.md), [U4c 결과](U4C-RESULTS.md), [U4 결과](U4-RESULTS.md).

사용자 요청: "이식본 디스크 읽기 편차 원인 찾기".

## 현상

- 같은 코드·같은 창에서 디스크 복원 시간이 run마다 크게 다르다. 8K checkpoint(0.8 GB)는 0.17 s 또는 1.1–1.5 s이고, 256K(17 GB)는 3.7–10.0 s이다.
- 느린 경우의 읽기 속도는 0.6–0.7 GB/s로 거의 일정하다. 빠른 경우는 4–5 GB/s다(복원 벽시계 기준).

## 결론

**SSD 자체가 느려진 것이다. 이식본 코드 때문이 아니다.**

- 장치는 Crucial P310 2TB(`CT2000P310SSD8`, QLC, DRAM 없음)이고, 파일시스템은 ext4다(`discard` 없음, 주간 `fstrim`, 마지막 실행 10-19).
- 큰 쓰기 직후에는 방금 쓴 데이터를 읽는 요청 하나하나가 8–10배 느려진다. 짧게 쉬어도 풀리지 않는다.
  - 이 쓰기는 창마다 5–19 GB이고, 하루 run 하나에 약 150 GB다.
- QLC 드라이브가 쓴 데이터를 SLC 캐시에서 QLC로 옮기는 동안 생기는 일로 본다. 장치 내부 상태는 볼 수 없으므로 이 부분은 추정이다.
- **TRIM으로 확인했다** (사용자: "니가 실행해도되").
  - `sudo fstrim -v /`가 392.3 GiB를 풀었다. 지운 테스트 캐시를 SSD가 빈 곳으로 모르고 있었다.
  - 그 뒤 호스트 재현은 12번 모두 3.3–3.7 GB/s였다(`diskcontend-c02`, 전에는 12번 중 11번이 0.36–0.74).
  - 서버 shared 창(`diskdiag-c01`)의 디스크 복원 12번도 모두 0.17–0.28 s였다(TTFT 0.38–0.49 s, 운영 RAM 경로 0.87 s). 전에는 둘째 턴이 1.06–1.54 s였다.

## 근거

1. **서버 안 측정** (`diskdiag-a01`, `diskdiag-b01`, 호스트 `/proc/diskstats` 20 ms 샘플, `iosample.py`)
   - 느린 복원과 빠른 복원은 읽기 바이트(0.8 GB)와 요청 크기(약 128 KB)가 같다.
   - 동시에 걸린 요청 수도 Little 법칙으로 약 10개로 같다. helper 8개가 앞서 읽고 있다는 뜻이다.
   - 다른 것은 요청 하나의 장치 지연뿐이다. 느릴 때 1.8–2.7 ms, 빠를 때 0.26–0.35 ms다.
   - shared 둘째 턴은 이번에도 1.06–1.54 s였다. 이때 같은 구간의 동시 쓰기는 0.01–0.28 GB로 작다.
   - 재시작 뒤 첫 복원은 1.11 s였고, 그다음 다섯 번은 0.17–0.19 s였다.
2. **호스트만으로 재현** (`diskcontend.py`, GPU·서버 없음)
   - 0.55 GB checkpoint 10개(5.5 GB)를 쓰고 첫 checkpoint를 읽었다.
   - 쉬는 시간 0–20 s 모두 0.36–0.74 GB/s였다(550 MB에 1.2–1.5 s, 서버의 느린 경우와 같다). 12번 중 한 번만 2.9 GB/s였다.
   - 같은 날 앞선 시도(`diskcontend-a01`, `-b01`)는 쓰기 직후에도 3.4–5.1 GB/s였다. 반복해서 쓰고 지우자 상태가 바뀌었다. 장치 상태에 따른다는 뜻이다.
3. **메모리 크기·여유 공간은 원인이 아니다.**
   - 2 GiB 창(f9-two8k)은 예전 run 4번 모두 느렸지만, 이번(`diskdiag-a01`)에는 8 GiB와 똑같이 빨랐다(0.8 GB를 77 ms에).
   - 여유 공간이 272 GB여도 shared는 느렸다. 다만 마지막 TRIM 뒤 지운 공간은 SSD가 빈 곳으로 모를 수 있다.

## 운영과 다르게 보이는 이유

- 운영도 같은 SSD를 쓴다. 이번 run에서 운영의 256K 복원도 5.9 s였다(대개 3.2–3.8 s).
- **운영은 덜 쓴다.** 창별 SSD 쓰기는 운영/이식본이 two8k 3.6/5.2, shared 6.1/9.6, regress 6.4/7.7, long32k 6.6/12.9 GB다. 저장 중복 제거를 하지 않기로 한 결정(D4)과 같은 비용이다.
- **shared 둘째 턴에서 이식본은 디스크를, 운영은 RAM을 고른다.**
  - 이식본은 RAM에 8,208이 있어도 더 깊은 디스크 8,421을 고른다(`selection_reason=2`). SSD가 건강하면 이쪽이 빠르다(0.38 s, 운영 RAM 경로 0.87 s). SSD가 느려지면 1.3–1.7 s가 된다.

## 남은 결정·후보

- **측정 조건:** 디스크 복원 TTFT는 SSD 상태에 따라 바뀐다. 앞으로 비교할 때는 창 사이 `fstrim`(root 필요) 여부와 장치 지연을 같이 기록한다. 운영과 이식본을 번갈아 돌리는 비교는 계속 유효하다.
- **TRIM 주기:** 테스트 캐시를 대량으로 지운 뒤에는 TRIM 전까지 SSD가 그 공간을 쓰지 못한다. 주간 `fstrim.timer`로는 부족하다. GPU run 전에 `fstrim`을 하거나 `discard` 마운트를 쓰는 것은 시스템 설정 변경이라 사용자가 정한다.
- **코드 후보(미결정):**
  - 디스크와 RAM 중 고를 때 측정한 디스크 속도로 비용을 비교한다. 지금은 깊은 쪽을 고른다.
  - 디스크 쓰기량을 줄인다. 단 저장 중복 제거는 D4에서 하지 않기로 했다.
  - 둘 다 SSD가 느려지는 것 자체를 고치지는 못한다.

증거는 `storage/evaluations/gufo-upstream-port-final-20261023/`에 있다.

- 호스트 재현: `diskcontend-a01.log`, `-b01.log`, `-c01.log`, TRIM 뒤 `-c02.log`.
